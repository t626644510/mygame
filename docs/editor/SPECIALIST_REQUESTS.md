# 给其他专项的需求说明

日期：2026-11-15。来源：编辑器规划（[EDITOR_PLAN.md](EDITOR_PLAN.md)）中，编辑器自身做不了、必须由其他专项补的部分。

P0 交付后，这些条目要录入 `content/_requests/`，成为需求单系统的第一批真实内容，之后以 `REQUESTS.md` 为准。本文件随即标为归档。

每条需求的“不卡”和“卡住”，都是相对编辑器各期而言，不代表对游戏开发本身的优先级判断；优先级由总策划定。

## R1 六维属性 → 战斗数值映射

- **归属：** 战斗专项
- **卡住：** 不卡。P2 用 `combatOverride` 手填过渡。

**背景**

- 项目已确认六项属性：力量、体质、智力、精神、敏捷、集中。
- 战斗运行时目前只读 `intelligence`，用来算指令容量。速度只用 `agilityFactor`，HP、MP 都直接配置。
- 其余五项在战斗里没有任何作用，编辑器只能先显示成“尚未接入”。

**要什么**

1. 一份公式说明，写清各属性影响哪些战斗量。候选包括：maxHp、maxMp、agilityFactor、伤害 / 治疗加成、状态抗性、MP 回复。没有作用的属性也要明说。
2. 一个纯 C# 的派生函数，例如 `CombatAttributes.Derive(attributes) → {maxHp, maxMp, agilityFactor, ...}`，放在 Combat Runtime。
3. 公式是否随等级变化；等级和成长是否也在这次定。

**不要什么**

- 不要求现在平衡数值，用试玩参数即可。和现有试玩参数一样，标明“可替换”。

**交付后编辑器怎么接**

- sim-cli 调用派生函数得到派生值。
- 角色页把 `combatOverride` 与公式结果不一致的地方标出来，由 User 决定保留覆盖值还是改用公式。

## R2 技能从战例中抽成全局技能库

- **归属：** 战斗专项 + 工程
- **卡住：** 不卡。P2 由组装器把技能拷进每份战例。

**背景**

- 技能现在定义在每份战例的 `actions[]` 里。
- 同一个 `mage_firebolt` 可能在多份战例里各有一份，靠 `ActionDefinitionsEquivalent` 判断是否相同。
- 编辑器已经按“全局一份”管理技能。

**要什么**

- 运行时可以从全局技能表加载技能，战例只引用技能 ID。
- 旧战例继续支持内嵌 `actions[]`，不破坏现有测试和报告重放。
- 内嵌与全局同 ID 但不等价时的处理规则（报错还是内嵌优先），由战斗专项定。

## R3 物品定义 / 实例分离，装备属性如何进入战斗

- **归属：** 工程（实例与归属）+ 战斗（装备投影）
- **卡住：**
  - P1 只做物品定义，不卡。
  - P2 装备投影只能用 `equipmentDamageBonus`。

**背景**

- 编辑器的物品表只存定义，比如“巡卫短剑”。
- 带强化等级、归属人、装备者的个体（如 `guard-linen-sword-001`），目前写在备战配置里，是运行时状态。
- 战斗目前只认 `equipmentDamageBonus` 一个装备字段。

**要什么**

1. 物品实例的数据结构和归属规则，包括：
   - 实例 ID 怎么生成
   - 定义 ID 如何引用
   - 公共 / 私人持有怎么记
2. 装备的其他属性怎么进入战斗：防御、MP 上限、速度、状态抗性等。需要战斗侧新增哪些字段，物品编辑器的 `combatBonusFields` 就跟着扩展。
3. 同一物品在战斗和基地两侧 ID 不一致的问题：
   - 战斗配置写 `expedition_ore`，基地写 `expedition-ore`，现在靠 `Expedition/default.json` 的 `itemMappings` 桥接。
   - 物品注册表上线后（P1 用 aliases 统一），这套桥接何时退役，由工程决定。

## R4 基地寻路支持障碍

- **归属：** 基地专项
- **卡住：** P3 的可达性检查和距离叠加。
- **规格：** 已写入 [P3_WORK_ORDER.md](P3_WORK_ORDER.md) 第 5 节，按那里交付。

**背景**

- `BaseSession.MoveToward` 固定先 x 后 y，场景里没有障碍。
- 一旦有建筑占地和障碍格，就需要真正的最短路。

**要点**

- 新增纯函数，不改 `BaseSession`。
- 无障碍时与现有路径逐格相同，保证首餐、备战测试不受影响。

## R5 居民决策模型 v0 与通用基地模拟

- **归属：** 基地专项
- **卡住：** P4（基地沙盘、行为档案）全部。

**已定方向（User 2026-11-15 确认）**

- 居民行为由策划按职业写“行为档案”。
- 行为档案沿用战斗的“按优先级逐条尝试”指令句式。
- 玩家只调税、福利、岗位优先级等政策，不逐个编辑居民。

**要什么（先交文档，评审通过后再写代码）**

一份《居民决策模型 v0》，至少回答以下问题。形式参照 `CombatTacticsCatalog`：每个目录项都有 id、label、说明、参数和单位。

1. **需求：** 有哪些需求（饥饿、疲劳、满意度等），怎么随时间变化，阈值和后果是什么。
2. **四个目录：**
   - 条件：读需求、现金、库存、时段、建筑状态等。
   - 对象：卖某物的人或店、自己的建筑、仓库、住处等。
   - 选择方式：最近、最便宜、库存最多等。
   - 行动：采购、生产、摆卖、进食、休息、搬运等。
3. **长动作：** 行动包含走路、等待、交易等阶段。中途被更高优先级的规则抢占时，已扣的钱货、已走的路怎么处理。
4. **资源竞争：** 多人去买最后一份货时的预约 / 锁定规则，保证账本不出现一物两卖。
5. **经济决策：** 定价、选择卖家、存钱比例，这些用参数表还是公式，参数放在哪。
6. **一天的顺序：** 税、福利、工资、阶级检查、消费的先后。可引用已确认的三阶存款、满意度归零离开等方向。
7. **玩家政策接口：** 玩家能调的政策具体有哪些，各影响模型里的哪个参数。

**之后的代码交付（另开施工单）**

- 通用基地模拟：建筑、配方、居民、交易预约，固定种子，可重放，逐 tick 现金守恒。
- 沿用首餐模块的账本和测试纪律。
- 规则目录要能被 sim-cli 导出，编辑器的行为档案页直接复用 P2 的 `RuleList` 组件。
