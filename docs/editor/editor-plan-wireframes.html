Helper 编辑器设计规划

给三个开发辅助编辑器（战斗、地图、物品）定好架构、数据格式、界面和分期验收，并回答“基地生产线怎么验证、居民行为要不要单独做编辑器”。执行由其他 Agent 负责，本页是他们的施工依据，也是我验收时对照的标准。

读取范围：PROJECT_CONTEXT、Combat / BaseEconomy 运行时与配置、第四轮交接 没有运行 Unity、没有跑测试
已拍板 · 2026-11-15

三项决定均按建议执行

1 · 编辑器做成什么

已定：本地网页编辑器 + 无头 C# 模拟器

网页负责界面，规则全部由一个直接编译现有 Runtime/*.cs 的命令行程序执行（第四轮报告脚本已经证明这些源码能脱离 Unity 编译）。好处：不碰 Unity 场景和 A/B 那条退出崩溃链路，Mac / Windows 都能用，界面迭代快。备选是 Unity EditorWindow，能直接调核心，但必须开着 Unity，界面开发慢。

2 · “角色 json” 指什么

已定：角色模板与战例分开

现在角色写在战例里（CombatScenario.units[]），技能也挂在每份战例的 actions[] 上。编辑器输出独立的角色模板和技能库，再由组装器拼出现有格式的战例，运行时一行不改。

3 · 居民行为谁来配

已定：策划配行为档案，玩家只调政策

居民上限 100 人，让玩家逐个写指令不现实。建议策划按职业写“行为档案”（沿用战斗的四段指令句式），玩家在游戏里只调税、福利、岗位优先级。这决定了基地是“宏观经营”还是“第二套指令编程”，属于玩法取舍。

现状

仓库里能直接用的，和缺的

战斗侧已经很适合接编辑器：数据全是平铺的公开字段，规则目录（条件 37、选择方式 24、效果 7 类、状态 9 类）由 CombatTacticsCatalog 运行时导出，编辑校验由 CombatSession 回传逐条原因。基地侧还是两段写死的剧本，没有物品、建筑、配方的注册表，编辑器需要先补数据模型。

领域现有可用编辑器的缺口
技能CombatActionConfig 13 个字段，27 个法师技能可执行技能挂在单份战例里，没有全局技能库；咏唱、暴击闪避、DoT、复活、移动未实现
角色CombatUnitConfig：HP/MP、智力、敏捷系数、指令、白名单、tags六维属性只有智力进了战斗字段；力量、体质、精神、集中没有映射公式
指令四段指令、1–3 项条件、AND/OR 分组、容量按智力计算，编辑 API 返回 validationReason无
物品出征掉落 itemId+quantity；强化消耗矿料 3 + 淬火砂 2没有物品定义表，ID 散落在各配置里；装备对战斗只有 equipmentDamageBonus 一个字段
建筑 / 地图10×5 格子图、预置厨房、按格计 tick 的移动没有建筑定义、没有摆放；寻路固定先 x 后 y，不支持障碍
生产 / 居民“购粮 → 加工 → 售餐”单链，账本守恒、可重放没有通用配方、居民需求和决策模型，只能跑这一条剧本
总体架构

一个编辑器外壳，一个规则来源

核心原则沿用项目已有的那条：界面读真实数据，不另写一套规则结算器。编辑器里所有“合不合法、跑出来什么结果”都问模拟器；编辑器自己只负责表单、摆放和展示。

格式硬规则

  • Unity JsonUtility 读不了字典、顶层数组和多态，所以 schema 只用对象 + 对象数组，键值对一律写成 [{id, value}]。
  • 每个文件带 schemaVersion；sim-cli 读写必须与 JsonUtility 往返一致（第三轮已经因为 null 数组踩过一次坑）。
  • 编辑源和运行时数据分开：备注、草稿、需求单只在 content/，export 时校验不过就不出包。

全局 ID 规则（三个编辑器共用）

规则做法
格式^[a-z][a-z0-9_]*$，带类型前缀：物品 mat_ eq_ con_ cur_ key_，角色 chr_，建筑 bld_，配方 rcp_，遭遇 enc_。现有 mage_*、expedition-ore 等旧 ID 原样保留，不强制改名。
唯一全内容库唯一（不是各类型内唯一），避免状态 ID 和物品 ID 撞名后报告看不懂。
不可变首次保存后 ID 输入框锁定，改名只改显示名。真要改 ID 走“迁移”：改写所有引用并在 aliases 留旧 ID。
删除被引用时禁止删除，显示“被 N 处引用”并可跳转；只能先改引用或标记弃用。
定义 vs 实例物品表只存定义（巡卫短剑）。带强化等级、归属人的个体（guard-linen-sword-001）是运行时状态，不进物品编辑器。

备注与需求单：给 Agent 的反馈通道

三个编辑器共用一套模型。任何实体、任何字段都能挂备注；备注分两种：纯备注（给自己看）和需求（要 Agent 去实现）。需求有归属专项和状态，sim-cli 把它们汇总成 REQUESTS.md，按战斗 / 基地 / 工程分组，Agent 只读这一个文件就知道要做什么。

{
  "schemaVersion": 1,
  "id": "REQ-0007",
  "kind": "new_effect",
  "owner": "combat",
  "target": "skill:mage_chant_meteor",
  "field": "effectKind",
  "title": "咏唱型技能：读条 60 WAIT 后落地",
  "body": "咏唱期间被打断则不消耗 MP……",
  "expected": "对全体敌人 40 魔法伤害",
  "status": "open",
  "createdAt": "2026-11-15",
  "resolvedBy": ""
}
  • kind：note、new_effect、new_condition、new_selector、new_status、new_building_function、new_item_property、balance、bug。
  • status：open → triaged → in_progress → done / rejected。只有总策划或 User 能把需求改成 triaged；Agent 完成后改 done 并填 resolvedBy（提交号）。
  • 占位实体：选了目录里没有的效果、条件或建筑功能，实体自动标 待实现，必须附一条需求才能保存；它能导出需求单，但进不了试跑和 export。
  • 某条需求 done 后，sim-cli 的目录里出现了对应能力，编辑器自动把占位实体的标记去掉，提示 User 复核。
编辑器 1

战斗编辑器

三块：技能库、角色模板、试炼场。核心交互是把四段指令读成一句中文，改一处立刻试跑，并和改之前那一版对比“第一处行动分歧”。项目里已经确认最好玩的就是“改指令能明显改变结果”，编辑器要把这一点放大。

指令编辑交互

  • 四个格子都是下拉，选项来自 sim-cli catalog，按 category 分组（资源 / 状态 / 队伍 / 站位 / 时间 / 标签），每项悬停显示 C# 里的 description。
  • 阈值按 thresholdUnit 显示：ratio 显示百分比、存 0–1；row 显示前/中/后排；wait、count、points 显示原单位。整数项禁止输入小数。
  • 每个条件项有“自身 / 目标”切换（对应 subject）。条件项数到 2 时出现 且/或，到 3 时出现括号位置切换（left / right），直接画出括号，不让人记 grouping。
  • 每次改动防抖 300ms 调 validate，用 C# 返回的 validationReason 标红，编辑器不自己算容量。
  • 技能下拉只列白名单里的技能；白名单在技能库侧边栏勾选，MP 不足不隐藏（与 GetAvailableActions 行为一致）。

试炼场

  • 对手来自 content/encounters/，敌人本身也是角色模板（team 在组装时决定），不另做敌人格式。
  • “与上次保存对比”调用现有 CombatSampleRuns 的对比逻辑，给出第一处行动分歧和结局差异。
  • 日志用 ExportLogText 原文，每行能跳回触发的指令；时间轴按 WAIT 画，每个角色一条泳道。
  • 支持连续场次（读 CombatExpeditionConfig）：看 HP/MP/状态跨场带入后第二场还撑不撑得住。

角色模板格式（编辑器产出）

{
  "schemaVersion": 1,
  "id": "chr_mage_apprentice",
  "name": "见习法师",
  "role": "combat",
  "tags": ["mage", "caster"],
  "attributes": [
    {"id": "strength", "value": 6},
    {"id": "constitution", "value": 9},
    {"id": "intelligence", "value": 40},
    {"id": "spirit", "value": 18},
    {"id": "agility", "value": 10},
    {"id": "focus", "value": 12}
  ],
  "combatOverride": {"maxHp": 100, "maxMp": 30,
                     "agilityFactor": 1.0},
  "availableActionIds": ["mage_firebolt", "..."],
  "instructions": [ /* 原样 CombatInstruction */ ],
  "defaultEquipment": [
    {"slot": "weapon", "itemId": "eq_training_staff"}
  ],
  "draft": false
}

两个导出

  • 导出角色 JSON：上面这份模板，给后续正式角色设计用。
  • 导出为战例：组装器把选中的角色 + 遭遇 + 引用到的技能拼成现有 CombatScenario，availableActionIdsExplicit 固定 true，能被现在的 Unity 原型直接加载。
  • combatOverride 是过渡字段：六维 → HP/MP/敏捷系数的公式没定之前手填；公式一旦进 C#，sim-cli 计算派生值，编辑器把手填项标成“与公式不一致”。
  • 装备只能把 equipmentDamageBonus 投到战斗里，这是目前唯一接通的字段。
编辑器 2

物品编辑器

物品是战斗掉落、强化、建筑造价、配方的共同依赖，所以排在第一个做。界面以表格为主（物品会很多，User 需要筛选和批量看），点一行从右侧滑出详情。最有用的一列是“来源 / 用途”：没有来源的材料、没人用的材料一眼就能看到。

{
  "schemaVersion": 1,
  "id": "eq_patrol_sword",
  "name": "巡卫短剑",
  "category": "equipment",
  "stackLimit": 1,
  "baseValue": 40,
  "tags": ["weapon", "public_issue"],
  "equipment": {
    "slot": "weapon",
    "combatBonus": [{"id": "equipmentDamageBonus", "value": 0}],
    "enhancement": [
      {"level": 1, "cash": 0, "attackBonusDelta": 4,
       "materials": [{"itemId": "expedition-ore", "quantity": 3},
                     {"itemId": "quenching-sand", "quantity": 2}]}
    ]
  },
  "draft": false
}
  • 按类型挂扩展块：equipment、consumable、material；类型切换时其他块清空并提示。
  • combatBonus 的可选项来自 sim-cli 的“已接通战斗字段”列表，目前只有一项；想加防御、命中等，选“其他（未实现）”自动生成需求。
  • 强化表直接复现第二轮样例（矿料 3 + 淬火砂 2 → 攻击 +4），P1 验收就用它对账。
  • “从表格粘贴”：User 在 Excel 里写好 ID / 名称 / 类型 / 价格几列，粘进来批量建，逐行显示冲突。
编辑器 3

地图编辑器（基地布局）

分两层：建筑定义（这种建筑多大、干什么、造价多少）和布局（哪座建筑放在哪）。布局画布最重要的辅助是“通行距离”叠加层：现在的基地模拟里，移动按格算 tick，首餐例子里厨房放近放远就是 7 tick 和 17 tick 的差别，摆放本身就是数值。

// content/buildings/bld_kitchen.json
{
  "schemaVersion": 1,
  "id": "bld_kitchen",
  "name": "厨房",
  "footprint": {"w": 2, "h": 2},
  "entrance": {"x": 1, "y": 2},
  "function": "workshop",
  "recipeIds": ["rcp_simple_meal"],
  "workSlots": 1,
  "storageSlots": 4,
  "ownership": "both",
  "buildCost": {"cash": 30, "workTicks": 40,
    "materials": [{"itemId": "mat_timber", "quantity": 6}]},
  "draft": false
}
  • function 目录：workshop（已有厨房这一例）、storage、housing、shop、public_service、decoration。除厨房外现在都没有运行时，编辑器能建但标“待实现”，用于先把建筑清单和造价想清楚。
  • 布局文件存地图尺寸、地形格、建筑实例（instanceId, buildingId, x, y, rotation, ownership）、居民出生点。
  • 校验：越界、重叠、入口被堵、不可达（基于和模拟器同一套寻路）、工坊离最近仓储超过阈值时提醒。
  • 建筑“生产什么”不在这里配，只引用配方 ID；配方在生产页配，避免一条信息两处改。
额外问题

生产线怎么验证，居民行为怎么定

直接回答：需要做，但不能照搬战斗编辑器，也不该现在就做行为编辑器。原因是基地模拟目前只会跑“购粮→加工→售餐”这一条写死的剧本，行为编辑器写出来的东西没有引擎去执行。正确顺序是先让生产线能被静态检查，同时请基地专项定居民决策模型，再做行为档案和沙盘。

层回答什么问题怎么做前置
1 静态链检查这条生产线在数据上通不通、赚不赚钱配方连成图（物品是点，配方是边）。查：缺来源的输入、走不通的死胡同、循环；每个配方的单位工时增值 =（产出参考价 − 投入参考价）÷ 工时。私营经营者靠差价活，增值 ≤ 0 的环节没人愿意做。物品 + 配方数据，现在就能做
2 账本推演跑 N 天后会不会断粮、钱去哪了、谁闲着sim-cli 无头跑通用基地模拟，固定种子，输出账本、库存曲线、每个居民的时间分配（走路 / 干活 / 等料 / 闲置）、现金守恒检查、瓶颈报告（哪个输入卡住了哪座建筑）。沿用首餐模块的“逐 tick 守恒 + 重放一致”纪律。基地专项先出通用模拟，需求
3 沙盘回放直观看到哪里堵、哪里绕路在布局画布上回放第 2 层的结果：居民小点移动、建筑亮灯表示工作中、红色表示缺料，底部时间轴可拖动。与战斗的单步 / 重放同一个思路。第 2 层

居民行为：复用指令句式，但它是另一种东西

建议把居民行为也写成“按优先级逐条尝试”的规则列表，原因是 User 已经熟悉这个思路，编辑器能复用同一个规则行组件，C# 侧也能复用“逐条求值、不满足就看下一条、每条给出跳过原因”的结构。一份厨师档案大概长这样：

⋮⋮1
当自身饥饿 ≥ 70去卖餐的店按最近→买来吃
⋮⋮2
当自有粮 < 1且现金 ≥ 粮价去卖粮的人按最便宜→采购 粮食
⋮⋮3
当原料足够去自己的厨房→生产 简餐
⋮⋮4
当自有简餐 ≥ 1去自己的厨房→摆卖
⋮⋮5
当总是去自己的民居→休息

但和战斗有四处本质不同，基地专项定模型时必须先回答：

  • 需求和时段：饥饿、疲劳、满意度随时间变化，规则条件要能读它们和“现在是白天还是夜里”。
  • 长动作可打断：战斗行动是瞬发 + WAIT；居民的“去采购”包括走路、等货、成交，中途饿了要不要放下？
  • 多人抢同一份资源：两个厨师去买最后一份粮，需要预约 / 锁定，否则账本会出现双花。
  • 经济决策：定价、买谁的、存不存钱，这些是公式而非条件，需要单独的参数表而不是写进规则。
分工建议：基地专项先写《居民决策模型 v0》，形式参照战斗目录（条件目录、对象目录、选择方式目录、行动目录），并实现通用求值器；目录一出来，编辑器的行为档案页就能按战斗指令页的同一个组件接上。已定：玩家只调政策和岗位优先级，不逐个编辑居民。
施工顺序

分期与验收标准

每期的验收项都是可以复核的实际结果，我按这些逐条收。前三期不依赖任何未定玩法，可以马上开始；第四期要等基地专项的模型。

我额外的建议

  • 编辑器不进游戏包。它是开发工具，单独放 tools/，不往 Unity 场景、Prefab 里加东西，也就不会和 A/B 退出崩溃的排查互相干扰。
  • 每个编辑器都带“改前 / 改后”对比。战斗看第一处分歧，物品看引用变化，布局看通行距离变化，生产看账本差异。项目一直在用“只改一项的对照”来验证设计，编辑器把这个变成一键操作。
  • 界面不要做成 Unity 那套 A/B/C 候选。这是内部工具，一套朴素、信息密的界面就够，省下的工夫放在校验和对比上。
